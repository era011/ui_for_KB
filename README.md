# Альфа Ойл — База знаний операторов

Внутренний сервис для загрузки, хранения и поиска материалов базы знаний (инструкции, памятки, FAQ и т.п.). Документы дробятся на смысловые фрагменты (чанки), векторизуются и складываются в Weaviate — на этих чанках строится retrieval для бота-ассистента операторов.

## Архитектура

```
Browser (JS/HTML/CSS, frontend/)
        │  fetch /api/*
        ▼
FastAPI (backend/main.py)
        │
        ├── Postgres  — метаданные документов (backend/db.py)
        │               • marketing_files — карточки документов
        │               • action_logs     — журнал действий (upload/delete)
        │
        └── Weaviate   — чанки + embeddings (backend/weaviate_funcs.py)
                          коллекция Marketing_chunks, вектор считает
                          OpenAI text-embedding-3-large через
                          встроенный text2vec_openai-модуль Weaviate
```

Frontend — статические файлы без сборки, FastAPI отдаёт их напрямую (`app.mount("/assets", ...)`).

## Стек

- **Backend:** FastAPI, uvicorn, psycopg2, weaviate-client, langchain-text-splitters, pypdf, python-docx
- **Frontend:** vanilla JS/HTML/CSS (без фреймворков и сборки)
- **Хранилища:** PostgreSQL (метаданные + логи), Weaviate (векторный поиск)
- **Embeddings:** OpenAI `text-embedding-3-large` (вызывается самим Weaviate по `X-OpenAI-Api-Key`)

## Переменные окружения (`.env`)

См. [`.env.example`](.env.example):

| Переменная | Назначение |
|---|---|
| `SERVER` | хост Postgres и Weaviate |
| `WEAVIATE_PORT` | HTTP-порт Weaviate (gRPC жёстко задан на `50051` в `backend/weaviate_client.py`) |
| `OPENAI_API_KEY` | ключ для векторизации через Weaviate |
| `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | подключение к Postgres |

## Запуск

### Docker (рекомендуется)

```bash
docker compose up -d --build
```

Поднимется на `http://localhost:8509` (проброс `8509 → 8501` внутри контейнера). Compose ожидает внешнюю docker-сеть `kb_default` — если её нет: `docker network create kb_default`.

### Локально

```bash
pip install -r requirements.txt
uvicorn backend.main:app --host 0.0.0.0 --port 8501 --reload
```

## API

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/documents?search=` | список документов (поиск по имени, `ILIKE`) |
| GET | `/api/documents/{id_doc}/chunks` | все чанки документа из Weaviate |
| DELETE | `/api/documents/{id_doc}?name=` | удалить документ из Postgres и Weaviate |
| POST | `/api/documents/upload` | загрузить один или несколько файлов (`multipart/form-data`, поле `files`) |
| GET | `/api/logs?limit=` | журнал последних действий |
| GET | `/api/health` | healthcheck |

## Поддерживаемые форматы файлов

`.txt`, `.pdf`, `.docx` (см. `SUPPORTED_EXTENSIONS` в `backend/weaviate_funcs.py`).

- **`.txt`** — читается как есть, сначала пробуется UTF-8, при неудаче — `cp1251`.
- **`.pdf`** — текст постранично извлекается через `pypdf` (`PdfReader.extract_text()`), страницы склеиваются через `\n\n`. Отсканированные PDF без текстового слоя (только картинки) текста не дадут — OCR не выполняется.
- **`.docx`** — через `python-docx` собираются все непустые параграфы, затем текст всех ячеек всех таблиц. Старый бинарный `.doc` не поддерживается — нужно пересохранить в `.docx`.

Если текст извлечь не удалось (пустая строка после обработки) — загрузка отклоняется с ошибкой.

## Логика чанкования

Реализована в `split_by_sections_then_textsplitter` (`backend/weaviate_funcs.py`) и запускается один раз на весь извлечённый текст документа. Два прохода:

**1. Разбиение на секции**

Текст нормализуется (`\r\n`/`\r` → `\n`) и режется по regex `\n\s*\n\s*\n+` — то есть по местам, где встречаются **две и более подряд идущих пустых строки**. Это грубое разбиение по крупным смысловым блокам документа (разделы, вопросы FAQ и т.п.), которые автор отделил явными пропусками. Пустые секции после `strip()` отбрасываются.

**2. Дробление каждой секции сплиттером**

Каждая непустая секция дополнительно режется через `RecursiveCharacterTextSplitter` (langchain) с параметрами:

- `chunk_size=1000`, `chunk_overlap=300` (символов)
- `separators=["\n\n", "\n", ". ", " ", ""]`

Сплиттер рекурсивно пытается резать сначала по абзацам, потом по строкам, потом по концу предложения, потом по пробелам, и только в крайнем случае — по символам, стараясь уложиться в `chunk_size` и не разрывать текст посреди слова/предложения без необходимости. Overlap в 300 символов между соседними чанками сохраняет контекст на стыке, чтобы фрагмент не терял смысл при выдёргивании ретривером.

**Зачем два прохода, а не один сплиттер сразу на весь текст:** секции задают авторские смысловые границы (например, разные вопросы в FAQ не должны склеиваться в один чанк даже если оба короче 1000 символов), а сплиттер внутри секции уже разруливает случаи, когда сама секция больше `chunk_size`.

**Метаданные каждого чанка:**

| Поле | Значение |
|---|---|
| `content` | текст чанка (единственное векторизуемое поле — `vectorize=True` в схеме Weaviate) |
| `name` | имя файла |
| `id_doc` | MD5-хеш полного извлечённого текста документа |
| `added_date_to_weaviate` | UTC-таймстамп загрузки |
| `chunk_index` | сквозной порядковый номер чанка по всему документу |

(`section_index` / `subchunk_index` считаются при нарезке, но в Weaviate не сохраняются — коллекция хранит только `chunk_index`.)

**Дедупликация:** `id_doc` — это MD5 от текста, а не от имени файла. Значит:
- один и тот же контент под разным именем файла будет распознан как дубликат и отклонён;
- любое изменение текста (даже на 1 символ) даёт новый `id_doc` — документ будет загружен как новый, а не обновлён поверх старого. Обновление документа = сначала удалить старую версию, затем загрузить новую.

**Векторизация:** только поле `content` векторизуется (`text2vec_openai`, модель `text-embedding-3-large`); остальные поля хранятся как обычные (не векторные) свойства и используются для фильтрации (`Filter.by_property("id_doc")`) и отображения в UI.

## Журнал действий (`action_logs`)

Каждая загрузка и удаление документа пишется в Postgres-таблицу `action_logs` (`action`, `status`, `doc_id`, `doc_name`, `message`, `created_at`) через `log_action()` в `backend/db.py`. Ошибка записи лога не прерывает основной запрос — она только печатается в консоль. Смотреть журнал можно в UI (кнопка «Логи») или через `GET /api/logs`.
